# Trace Algorithms

This document explains the logic behind the trace workflows in `lifelike_gds`,
with emphasis on the radiate analysis and how trace paths are selected.

## Summary

The project has two main trace styles:

- shortest-path traces: find shortest paths between source and target node sets
- radiate traces: rank nodes by source-seeded personalized PageRank, then build
  traces that prefer highly ranked nodes

The code uses NetworkX graph objects directly, with custom wrappers for node
sets, export metadata, and trace-network payloads.

## Graph Types

The tracing classes default to `nx.MultiDiGraph`, not `nx.DiGraph`.

- `DiGraph` allows at most one directed edge from `u` to `v`
- `MultiDiGraph` allows multiple parallel directed edges from `u` to `v`

This matters for pathway data because multiple biological relationships may
exist between the same pair of nodes and need to be preserved separately.

`TraceGraphNx` chooses the backend in its constructor:

- `multigraph=True` -> `MultiDirectedGraph(nx.MultiDiGraph())`
- `multigraph=False` -> `DirectedGraph(nx.DiGraph())`

The example radiate scripts instantiate `RadiateTrace(graphsource)` without
overriding `multigraph`, so the examples use the multigraph backend by default.

## Shortest-Path Traces

The core entry point is `add_trace_network()` in
`src/lifelike_gds/network/trace_utils.py`.

Depending on the arguments, it creates trace networks using one of these modes:

- `weight is None`: unweighted shortest paths
- `weight is not None`: weighted shortest paths minimizing edge-weight sum
- `maxsum is not None`: shortest paths after converting node scores into edge
  costs that favor high-scoring nodes
- `minsum is not None`: analogous path search favoring low node scores

The shortest-path helpers ultimately rely on NetworkX shortest-path routines,
especially `nx.all_shortest_paths`.

## Radiate Analysis

Radiate analysis is implemented in `src/lifelike_gds/network/radiate_trace.py`.

It has two phases:

1. rank nodes by source-seeded personalized PageRank
2. build trace paths that prefer high-ranking nodes

### Ranking Phase

The ranking helper is `pagerank_influence()` in
`src/lifelike_gds/network/trace_graph_utils.py`.

For a named source set:

1. create a personalization vector over all nodes
2. assign value `1` to each source node and `0` to non-source nodes
3. apply any user-provided overrides from the `personalization` argument
4. run `nx.pagerank(...)` with that personalization vector

This is best described as:

- directed personalized PageRank
- source-seeded personalized PageRank
- random walk with restart implemented through PageRank personalization

The code previously used the local variable name `nstart`, but that was
misleading. In NetworkX, `nstart` means the initial iterate for the power
method. Here the values are passed as the `personalization` argument, so they
represent the restart or teleportation distribution instead.

### Forward and Reverse Ranking

Radiate analysis supports:

- forward ranking: personalized PageRank on the graph as stored
- reverse ranking: personalized PageRank on the edge-reversed graph

Forward ranking answers:

- which nodes are strongly influenced downstream from the source set?

Reverse ranking answers:

- which nodes have strong influence paths into the source set when edges are
  traversed in reverse?

The reverse calculation is implemented by calling `graph.reverse()` before
running the same personalized PageRank helper.

### Reach Counts

Radiate also computes a reachability count with `set_nReach()`.

This is separate from PageRank. For each source node, the code calls
`nx.single_source_shortest_path(...)` and increments a counter for every node
that is reachable from that source.

That produces:

- `nReach`: number of source nodes that can reach a node
- `rev_nReach`: number of source nodes reachable from a node in reverse mode

These are path-reachability counts, not diffusion scores.

### Building High-Influence Traces

After node ranking, the radiate trace builder creates path networks using
`add_trace_network(..., maxsum=<rank_property>)`.

The helper `all_node_maxsum_paths()` converts the node rank into temporary edge
costs using the source node's score:

- edge cost = `1 / source_node_rank` when the rank is positive
- edge cost = a very large number when the rank is zero

Then the code calls `nx.all_shortest_paths` on those temporary edge costs.

This means the "highest influence" traces are not generated by following the
random walk directly. Instead, they are shortest paths in a transformed graph
where passing through highly ranked nodes is cheaper.

## Combining Forward and Reverse Ranks

The helper `set_intersection_pagerank()` combines two existing node scores:

- `p1`: forward personalized PageRank from a source set
- `p2`: reverse personalized PageRank from a target set

It computes:

`p1 * p2 / (p1 + p2 - p1 * p2)`

This is the Hamacher product, a standard fuzzy-intersection operator. It is
useful when we want nodes to rank high only if they are strong in both
directions.

Important note:

- this is not a standard PageRank variant
- this function does not run another PageRank pass
- for external communication, it is more accurate to call this a
  bidirectional overlap score or bidirectional influence score

## NetworkX Algorithms Used

The trace workflows rely mainly on these NetworkX functions:

- `nx.pagerank`
- `nx.all_shortest_paths`
- `nx.single_source_shortest_path`
- graph reversal via `G.reverse()`

The repository currently depends on `networkx>=3.6.1`.

## Recommended External Terminology

For communication with outside teams or researchers, the clearest terms are:

- radiate ranking: source-seeded directed personalized PageRank
- reverse radiate ranking: personalized PageRank on the reversed graph
- radiate traces: inverse-rank shortest-path traces derived from personalized
  PageRank scores
- combined forward/reverse score: bidirectional influence overlap score

These terms match the actual implementation closely without overstating that
every step is a single standard algorithm.
